### Security

- **The sandbox profile promises not to mount the container-engine socket of the host, and the built-in feature `docker-cli` declares such a mount.** `docker-cli` installs the feature `docker-outside-of-docker`; its metadata declare a bind mount of `/var/run/docker.sock`, and the Dev Container CLI merges the mounts of a feature into the start of the container (read in the metadata and in the source of the CLI `0.89.0`). A process in the container that can use the socket has root-equivalent access to the engine of the host. From `v0.6.0` to `v0.13.0` the generator rendered the feature in both profiles without a warning. Rated High (CVSS 3.1, `CVSS:3.1/AV:L/AC:H/PR:L/UI:N/S:C/C:H/I:H/A:H`, 7.8) in the GitHub Security Advisory that is published with the tag; there is no CVE.
  **Measured:** in the standard profile one Docker test starts a project with `docker-cli` and finds the bind mount of `/var/run/docker.sock` (as `/var/run/docker-host.sock`) in the container (Linux `amd64`, Docker 29.9.2, two runs on 2026-10-22), with the option `moby: false` set by hand in the rendered key. **Not measured:** the sandbox profile before this release, and the mount with the default option `moby: true`.
  **Whether a project is affected depends on the base image.** On the current default base image of the generated Dockerfile (`mcr.microsoft.com/devcontainers/base:debian`, Debian 13 `trixie` on the day of the test) the build with the default option stopped in one run on 2026-10-22 with "The 'moby' option is not supported on debian 'trixie'", so no container started. A container that was built with the feature earlier, or on another base image, carries the mount according to the metadata (read, not measured there).
  **What to do** if a project with the sandbox profile used `docker-cli`: disable the feature with `u-boot config set devcontainer.features.docker-cli.enabled false`; whoever needs Docker inside the container also sets `u-boot config set devcontainer.sandbox.nestedRuntime docker` (the profile then gets `--privileged`); run `u-boot generate devcontainer` again; recreate the container with `u-boot devcontainer up --recreate`, or rebuild it in the editor. **An existing container keeps the socket until it is recreated** (read, not measured: the mounts of a container are fixed when it is created). `u-boot doctor` reports the state of the project configuration (exit code `11`).
  In the standard profile `docker-cli` stays selectable; the socket is mounted there when the feature is enabled, which the disclosure of `u-boot devcontainer up` and the manual now say.
