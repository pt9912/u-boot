## 1. Ziel und Abgrenzung

**Ziel:** Messen und entwerfen, ob und wie `u-boot` den Devcontainer eines Projekts ohne Editor und ohne Host-Installation von Node oder der Dev-Container-CLI starten kann, sodass auf dem Host nur Docker nötig bleibt — und die Entscheidung für einen Weg (oder für den Status quo mit klarer Voraussetzung) in einem ADR vorlegen. **Messung und Entwurf, kein Produktcode:** die Umsetzung ist ein Folge-Slice nach Freigabe.

### Gefundener Stand (gelesen am 2026-10-18)

- **`u-boot` erzeugt nur Dateien, es startet den Devcontainer nicht.** Handbuch `docs/user/benutzerhandbuch.md` Abschnitt 4.9, *Voraussetzung*: „Zum Starten des Devcontainers brauchen Sie einen Devcontainer-fähigen Editor (zum Beispiel VS Code) oder die `devcontainer`-CLI.“ Abschnitt *Ergebnis*: `.devcontainer/devcontainer.json` und `.devcontainer/Dockerfile` entstehen. [`LH-FA-DEV-001`](../../../../spec/lastenheft.md#lh-fa-dev-001--devcontainer-erzeugen) nennt als Mindestdateien nur diese beiden. Die Befehle des Binary sind `init`, `doctor`, `add`, `remove`, `up`, `down`, `logs`, `generate`, `config`, `template` (`internal/adapter/driving/cli/root.go`, die `AddCommand`-Zeilen; `egress` kommt mit dem Slice [`slice-v1-cli-egress-anzeige`](../done/slice-v1-cli-egress-anzeige.md)). `u-boot up` betrifft den Compose-Stack: `internal/adapter/driving/cli/up.go`, Langtext von `newUpCommand` („Bring the Compose environment defined in compose.yaml up via docker compose up -d“).
- **Docker-Aufrufe des Hosts sitzen in einem Adapter-Paket.** `internal/hexagon/port/driven/docker.go` (`DockerProbe`), `docker_engine.go` (`DockerEngine`: `docker compose …`, Sentinels `ErrDockerUnavailable` → Exit-Code 11, `ErrComposeRuntime` → 12) und `devcontainer_inspector.go` (`DevcontainerInspector`: `FindContainer` über das Label `devcontainer.local_folder=<absoluter Ordner>`, `ReadFile` über `docker cp`); Implementierung in `internal/adapter/driven/docker/` (`engine.go`, `inspector.go`). Der Inspector verlangt einen absoluten Pfad mit führendem `/` (`FindContainer`, Prüfung am Anfang) und weist eine entfernte Engine ab (`requireLocalEngine`: `DOCKER_HOST` oder `docker context inspect`, nur `unix://` gilt als lokal, sonst `ErrContainerEngineNotLocal`). Einen Port, der einen Container **startet**, gibt es nicht.
- **Was das erzeugte `devcontainer.json` von dem Werkzeug verlangt** (`internal/hexagon/application/templates/devcontainer/devcontainer.json.tmpl`): `build.dockerfile` mit Kontext `.` und optional `USER_UID` als Build-Argument; im Sandbox-Profil `workspaceMount: ""`, ein benanntes Volume `…-${devcontainerId}` als Workspace, `runArgs`, `postCreateCommand`, `postStartCommand`, `remoteEnv` mit `${localEnv:GIT_TOKEN}` und weiteren Agent-Variablen; `features` aus dem Katalog; `remoteUser: vscode`. `updateRemoteUserUID` und `initializeCommand` setzt die Vorlage nicht (bei der Suche in `internal/hexagon/application` nicht gefunden). Im Standardprofil bindet das Werkzeug den Projektordner ein (Handbuch 4.9, *Hinweise*: „Das Standardprofil bindet den Projektordner ein“) — der **Host-Pfad** spielt dort eine Rolle.
- **Die Dev-Container-CLI ist schon gemessen — in einem Wegwerf-Container.** Messprotokoll [`messung-slice-v1-sandbox-egress-neuladen-entwurf`](../observations/BEO-DOK/messprotokoll-ausserhalb-des-repos/evidence/messung-slice-v1-sandbox-egress-neuladen-entwurf/README.md): `Dockerfile.cli` (`FROM docker:29-cli`, `FROM node:22-bookworm`, `COPY` des `docker`-Binary und von `docker-buildx`, `RUN npm install -g @devcontainers/cli`; Version 0.89.0 steht in `rohdaten-05-m4.txt`), Aufruf in `05-m4-neustart.sh` (Funktion `dc`): `docker run --rm -v /var/run/docker.sock:/var/run/docker.sock -v "$w":/w <cli-image> devcontainer up --workspace-folder /w/proj`. Gemessen (Colima 0.10.3, Docker 29.5.2, arm64, ein Lauf je Fall): `up` legt den Container an und führt `postStartCommand` aus; Ausgabe der CLI: Protokoll auf stderr, letzte Zeile ein JSON-Dokument mit `outcome`, `containerId`, `remoteUser`, `remoteWorkspaceFolder`; Stop und `up` startet denselben Container neu mit dem alten Image; `up --remove-existing-container` baut neu (Ergebnis in [`ADR-0025`](../../adr/0025-egress-liste-im-laufenden-container.md), Messung M4). **Nicht gemessen** ist dort: ein Projekt unter dem Pfad des Hosts (der Messordner liegt im Container unter `/w/proj`, das Label trägt diesen Pfad, nicht den des Hosts), Standardprofil mit Bind-Mount, `updateRemoteUserUID`, jede andere Engine als Colima, und der Vergleich mit einem Editor-Start.
- **Das Runtime-Image trägt weder Docker noch Shell.** `Dockerfile`, Stufe `runtime`: `FROM gcr.io/distroless/static-debian12:nonroot`, nur `/usr/local/bin/u-boot`, `USER 65532:65532`. Handbuch 2, *Container-Image*: „Auch `up`, `down` und `logs` laufen im Image nicht, weil dort kein Docker vorhanden ist.“ [`LH-NFA-PORT-004`](../../../../spec/lastenheft.md#lh-nfa-port-004--ausgeliefertes-container-image) schreibt „minimal … keine Shell und keine Build-Toolchain, … Non-root-Benutzer“ vor. Die Stufe `test-docker-tools` desselben `Dockerfile` bringt `docker-ce-cli` und das Compose-Plugin aus dem Docker-APT-Repo, `repo.mk` (`test-docker`, `image-scan`) hängt `/var/run/docker.sock` in einen Container: Muster im Repo vorhanden.
- **Distribution.** [`ADR-0007`](../../adr/0007-distributionswege-ghcr.md): GHCR-Image `ghcr.io/pt9912/u-boot` plus Binary; `npm package` ist dort **verworfen** („Go-Binary ist kein Node-Modul“) — das betrifft die Distribution von `u-boot`, nicht den Einsatz der Dev-Container-CLI als Werkzeug. `docs/maintainer/releasing.md` §1: der Tag-Push baut und veröffentlicht genau ein Image; ein zweites Image wäre ein neuer Release-Schritt.

## 6. Risiken und offene Punkte

- **Der Docker-Socket im Hilfs-Container ist Root auf dem Host-Docker.** — **Ausgang:** weiter offen bis S6; Haltung und Ausweisung entscheidet das ADR und der Projektinhaber.
- **Die Pfad-Abbildung stimmt auf Hosts außerhalb des Messstands nicht** (Windows, Docker Desktop, Colima mit Projekt außerhalb des Homes, entfernte Engine); ein falscher Pfad kann still einen falschen Bind-Mount erzeugen. — **Ausgang:** weiter offen bis S2 und S7; Zusage nur für Gemessenes.
- **Neue Lieferkette** (npm-Paket mit Abhängigkeiten, Node-Basisimage, Docker-CLI-Quelle) und Pin-Pflege (neue Advisories im Image-Scan). — **Ausgang:** weiter offen bis S5; Pin-Form nach dem Muster von [`ADR-0023`](../../adr/0023-podman-aus-podman-static-im-sandbox-devcontainer.md) und [`ADR-0024`](../../adr/0024-ollama-im-sandbox-devcontainer.md).
- **Ein per `u-boot` gestarteter Container weicht vom Editor-Start ab** (Labels, `${devcontainerId}`, Volumes); zwei getrennte Umgebungen wären die Folge. — **Ausgang:** weiter offen bis S9; ohne VS Code im Messaufbau bleibt es eine ausgewiesene Grenze.
- **Eine neue Zusage ohne Freigabe:** ein Befehl, der Container startet, ist im Lastenheft nicht vorgesehen. — **Ausgang:** weiter offen; Wortlaut-Vorschlag in §7, Freigabe des Projektinhabers vor einem CR-Slice ([`BEO-DOK/vertragsaenderung-nach-review`](../observations/BEO-DOK/vertragsaenderung-nach-review/observation.md): Vertragsänderungen fielen im Review auf).
- **Die Messung selbst läuft mit Host-Werkzeugen außerhalb von Docker** (Vorgänger-Protokolle nutzten `grep`, `head`, `tail`, `cut`, `sed` am Host). — **Ausgang:** weiter offen → [`BEO-WZG/host-werkzeug-ausserhalb-docker`](../observations/BEO-WZG/host-werkzeug-ausserhalb-docker/observation.md); die DoD verlangt `make` und Docker.
- **Die Messung gilt nur für Colima/arm64 und die CLI-Version zur Messzeit.** — **Ausgang:** weiter offen; Grenze in ADR und Protokoll.
- **Der Slice wächst in Richtung Umsetzung** (Option c oder Code „nur zum Probieren“). — **Ausgang:** weiter offen; Rückführung `in-progress` → `next` (§4), Code gehört in einen Folge-Slice.

### Offene Fragen an den Projektinhaber (vor dem Start oder spätestens im ADR)

1. **Reichweite „nur Docker“:** gilt das Ziel auch für Windows-Hosts (Pfad-Abbildung dort ungemessen), oder genügt Linux und macOS mit Colima?

4. **Befehlsform und Priorität:** `u-boot devcontainer up`/`down` (Vorschlag) oder ein Flag an `generate devcontainer`; Priorität V1 oder V2; Release-Zuordnung.
5. **Vorhandene CLI bevorzugen** (Variante a′) oder immer das Hilfs-Image?
