## Kontext

`u-boot` erzeugt `.devcontainer/devcontainer.json` und `.devcontainer/Dockerfile` ([`LH-FA-DEV-001`](../../../spec/lastenheft.md#lh-fa-dev-001--devcontainer-erzeugen)), startet den Container aber nicht. Wer ihn startet, braucht einen Devcontainer-fähigen Editor oder die `devcontainer`-CLI, also Node (Handbuch Abschnitt 4.9, *Voraussetzung*). Der Projektinhaber will mit weniger Werkzeugen auskommen (2026-10-18) und hat am 2026-10-20 entschieden: Reichweite Linux und macOS mit Colima, Windows nicht zugesagt; Beschaffung **a2** (Hilfs-Image lokal aus eingebettetem Dockerfile); der Docker-Socket darf in einen kurzlebigen Hilfs-Container und wird als Sicherheitslockerung ausgewiesen; Befehlsform `u-boot devcontainer up` / `down`; eine vorhandene `devcontainer`-CLI wird nicht bevorzugt (a′ entfällt). Diese ADR begründet und konkretisiert das; **eine neue Messung gibt es nicht** (Entscheidung des Projektinhabers).

**Belegbasis (gelesen am 2026-10-20).** [Messprotokoll](../../messungen/slice-v1-sandbox-egress-neuladen-entwurf/README.md), Schritt 4, Rohdaten [`rohdaten-05-m4.txt`](../../messungen/slice-v1-sandbox-egress-neuladen-entwurf/rohdaten-05-m4.txt). Messstand: Dev-Container-CLI 0.89.0 (Node.js v22.23.3) in einem Wegwerf-Container aus `Dockerfile.cli` (`FROM docker:29-cli`, `FROM node:22-bookworm`, `npm install -g @devcontainers/cli`, Tags ohne Digest, ohne `USER`), Colima 0.10.3, Docker 29.5.2 (Server), arm64, **ein Lauf je Fall**, Sandbox-Profil mit Egress. Aufruf: `docker run --rm -v /var/run/docker.sock:/var/run/docker.sock -v "$w":/w <cli-image> devcontainer up --workspace-folder <ordner>`. Das Skript gibt nur die letzten drei Zeilen der zusammengeführten Ausgabe (`2>&1`) weiter.

| Gemessen | Beleg |
|---|---|
| `up` legt den Container an; die letzte Zeile ist JSON mit `outcome: success`, `containerId` (64 Hexzeichen), `remoteUser: vscode`, `remoteWorkspaceFolder: /workspaces/egressprobe`; das `postStartCommand` lief (Statusdatei `result=ok`) | `rohdaten-05-m4.txt` Z. 4–15 |
| Stop, dann `up`: gleiche `containerId`, gleiches Image, Statusdatei neu geschrieben (`at=` später) | Z. 29–41 |
| `up` gegen den laufenden Container nach geänderter Liste auf dem Host: nichts ändert sich (Container, Image, Statusdatei) | Z. 42–53 |
| `up --remove-existing-container`: neue `containerId`, neues Image, geänderte Liste wirksam; keine Zombie-Prozesse | Z. 54–66 |

**Stand im Code (gelesen 2026-10-20).** Es gibt keinen Port, der einen Container **startet**. `internal/hexagon/port/driven/devcontainer_inspector.go`: `DevcontainerInspector` findet den Container über das Label `devcontainer.local_folder=<absoluter Ordner>` und liest Dateien mit `docker cp`. `internal/adapter/driven/docker/inspector.go`: `requireLocalEngine` weist eine entfernte Engine ab (`DOCKER_HOST` oder `docker context inspect`, nur `unix://` gilt als lokal). `internal/adapter/driven/docker/engine.go`: `preflight` prüft **drei** Schritte, darunter das Compose-Plugin. `internal/adapter/driving/cli/cli.go`, `ExitCode`: `driven.ErrDockerUnavailable` → 11, `driven.ErrComposeRuntime` → 12. `internal/adapter/driving/cli/egress.go`: `egress list` lehnt `--dry-run`/`--diff` mit Exit 2 ab (`ErrEgressPreviewNotApplicable`); `docs/maintainer/cli-json-contract.md` §2.2: `--quiet` ist im JSON-Modus ein No-op. Das erzeugte `devcontainer.json` reicht Zugangsdaten über `remoteEnv` mit `${localEnv:<NAME>}` durch (`templates/devcontainer/devcontainer.json.tmpl`, Zeilen 34 und 36: `GIT_TOKEN` und die Variablen eines Agenten); `${localWorkspaceFolder}` kommt in der Vorlage nicht vor. `make test-docker` (`repo.mk`) führt die Tests in einem Container aus, der den Docker-Socket und `/tmp` des Hosts **unter demselben Pfad** einhängt. `internal/e2e/sandbox_status_docker_test.go` bildet die Dev-Container-CLI nach (Label, `docker exec` der Lebenszyklus-Befehle); die echte CLI läuft in keinem Test.

**Nicht gemessen, nicht zugesagt** (jede Zeile ist Prüfauftrag des Umsetzungs-Slice, Entscheidung 9):

- **Das Ausgelieferte.** Der Messweg ist ein Wegwerf-Image mit ungepinnten Tags; das eingebettete, gepinnte Hilfs-Image (Entscheidung 2) und der Befehl sind nicht gemessen. Eine Messung an der Variante belegt nicht die Auslieferung (Beobachtung `BEO-DOK/messvariante-belegt-nicht-die-auslieferung`).
- **Pfad-Abbildung (S2).** Im Protokoll lag das Projekt im Hilfs-Container unter `/w/…`; das Label `devcontainer.local_folder` trägt den Pfad, den die CLI sieht. Dass ein gespiegelter Host-Pfad den Wert des Hosts ergibt und `FindContainer` den Container findet, ist Schluss, nicht Messung.
- **Standardprofil, `updateRemoteUserUID`, `USER_UID` auf einem Linux-Host mit anderer UID (S1, S3).** Das Protokoll läuft im Sandbox-Profil (Workspace im Volume); das Standardprofil bindet den Projektordner ein.
- **Socket-Haltung (S6):** dass der gestartete Container den Socket nicht trägt, dass der Hilfs-Container mit dem Befehl verschwindet, dass `${localEnv:<NAME>}` durchgereicht wird (im Messlauf bekam der Hilfs-Container keine Umgebung).
- **Lieferkette (S5):** Digest-Pins, Lockfile, Größe, Bauzeit, Image-Scan.
- **Andere Engines und Hosts (S7):** Linux-Host, Docker Desktop, Podman, entfernte Engine, Windows, `amd64`.
- **Fehlerbild (S8):** Exit-Codes und Ausgabe der CLI bei fehlendem Docker, falschem Pfad, Build-Fehler, Fehler im `postStartCommand`; welche Ausgabe auf stdout, welche auf stderr liegt (der Messlauf führt beide zusammen).
- **Editor-Vergleich (S9):** ob VS Code dieselben Labels und `${devcontainerId}`-Werte erzeugt. **Dauer** kalt und warm.

## Entscheidung

Jede Entscheidung nennt die Gegenoption, die verworfen wird.

1. **Weg a2: `u-boot` baut das Hilfs-Image lokal aus einem eingebetteten Kontext.** Der Kontext besteht aus `Dockerfile`, `package.json` und `package-lock.json`, eingebettet per `go:embed` im Driven-Adapter (nicht in der Application: es ist ein Implementierungsdetail des Ports aus Entscheidung 7). Der Adapter übergibt ihn als Tar-Strom an `docker build -` (kein Verzeichnis auf der Platte, kein Zugriff auf den Projektordner). Das Image trägt einen Tag aus CLI-Version und Hash der eingebetteten Dateien; `docker image inspect` entscheidet, ob gebaut wird, eine Pin-Hebung ändert den Hash und baut von selbst neu. Der erste Aufruf braucht Netzzugriff (npm-Registry, Basis-Images); ein Offline-Erststart ist nicht zugesagt. Alte Hilfs-Images räumt `u-boot` nicht ab (nicht zugesagt; `docker image prune` bleibt Sache des Nutzers). **Gegenoptionen:** a1 (GHCR-Artefakt) — ein neuer Release-Schritt ([`ADR-0007`](0007-distributionswege-ghcr.md), `docs/maintainer/releasing.md` §1), den der Projektinhaber abgewählt hat, und ein Artefakt, das ein Nutzer ohne Registry-Zugang nicht beziehen kann; a′ (vorhandene `devcontainer`-CLI bevorzugen) — zwei Pfade mit gleicher Zusage wären doppelt zu prüfen (Entscheidung des Projektinhabers).

2. **Lieferkette, Pin-Form g1 (Muster [ADR-0023](0023-podman-aus-podman-static-im-sandbox-devcontainer.md) und [ADR-0024](0024-ollama-im-sandbox-devcontainer.md), Auslegung von [`LH-NFA-SEC-004`](../../../spec/lastenheft.md#lh-nfa-sec-004--keine-verdeckte-ausführung-fremder-skripte)).**
   - **Pins stehen in den eingebetteten Dateien:** `FROM node:22-bookworm@sha256:<Digest des Index>` und die Docker-CLI (samt `buildx`-Plugin, wie im Messweg; das Compose-Plugin ist nicht Teil) aus `docker:29-cli@sha256:<Digest des Index>`; `@devcontainers/cli` in `package.json` auf eine **exakte** Version, `package-lock.json` mit den `integrity`-Hashes des ganzen Abhängigkeitsbaums, Installation mit `npm ci`. Versionslinien sind die gemessenen (CLI 0.89.0, Node 22, Docker-CLI 29); eine andere CLI-Version ist zulässig, wenn die Docker-Tests des Umsetzungs-Slice mit ihr laufen. **Die Digests und die Lockdatei setzt der Umsetzungs-Slice** (nicht gemessen, keine Zahl in dieser ADR).
   - **Ziel `--ignore-scripts`:** Die Installationsskripte der Abhängigkeiten laufen nicht. Trägt das nicht (die CLI startet danach nicht), geht der Umsetzungs-Slice zurück an den Architect; er nimmt keine Ausnahme still auf.
   - **Pflege wie [ADR-0024](0024-ollama-im-sandbox-devcontainer.md) Entscheidung 9:** Eine Hebung (CLI, Lockdatei, Digests) bei unveränderter Quelle und Prüfform ist ein Slice mit Wiederholung der Docker-Tests und ohne Folge-ADR; Trigger sind Ereignisse (Sicherheitsmeldung zur CLI oder ihren Abhängigkeiten, Ende der Wartung der Node-Linie, neue Hauptversion der CLI), kein Datum. Eine Folge-ADR braucht der Wechsel der Quelle (etwa a1), eine geänderte Prüfform oder ein Ausscheren aus `npm ci`. Der Pin ist ein Stand, kein Zustand; das ist der dritte gepinnte Download im Repo und wird in `BEO-APP/podman-static-pin-alterung`-Art im Register geführt (Umsetzungs-Slice).
   - **Auslegung von [`LH-NFA-SEC-004`](../../../spec/lastenheft.md#lh-nfa-sec-004--keine-verdeckte-ausführung-fremder-skripte):** Der Befehl führt gepinnten externen Code aus (npm-Pakete, zwei Basis-Images). Die ausdrückliche Zustimmung ist der Aufruf des Befehls, dessen Zweck diese Ausführung ist; die Quellen stehen im `--help`-Langtext und im Handbuch, die Ausführung bleibt auf den Hilfs-Container begrenzt. Der Pin schützt vor späterem Austausch, nicht davor, dass eine gepinnte Version von Anfang an schadhaft war. Das bestätigt der Projektinhaber mit `Accepted` (Freigabe-Punkt e).
   - **Akzeptiertes Negativ: kein Dauer-Scan des Hilfs-Images** in `make image-scan`. Das Image wird beim Nutzer gebaut und nicht ausgeliefert; die Pflege läuft über die Ereignis-Trigger oben. Der Umsetzungs-Slice misst **einmal** Trivy HIGH/CRITICAL, Größe und Bauzeit und weist das Ergebnis im Handbuch als Einzelmessung aus. **Gegenoption:** `npm install -g` ohne Lockdatei und Tags ohne Digest (der Messweg) — jede Ausführung kann andere Pakete ziehen; eine Messung gälte nicht für den nächsten Bau.

3. **Befehlsform und Verhalten.** `u-boot devcontainer up` und `u-boot devcontainer down`; Projektordner ist das Basisverzeichnis des Befehls (wie `up` und `down`), ohne Verzeichnis-Option.
   - **`up`:** startet den Container des Projekts mit `devcontainer up --workspace-folder <Ordner>` im Hilfs-Container (Entscheidung 4). Die Option `--recreate` ergänzt `--remove-existing-container` (gemessen nach geänderter Liste auf dem Host: neuer Container, neues Image; ohne geänderten Kontext ist das Image nicht gemessen). Weitere Optionen der CLI (etwa `--build-no-cache`) sind nicht Teil; sie lassen sich ohne Folge-ADR ergänzen. `up` prüft vorher mit dem Dateisystem-Port, dass `.devcontainer/devcontainer.json` existiert. Danach liest `up` die Ergebniszeile der CLI (letzte nicht leere Zeile der Standardausgabe; Felder `outcome`, `containerId`, `remoteUser`, `remoteWorkspaceFolder`, gemessen) und weist die Fallbacks des gestarteten Containers über die vorhandene Ausweisung aus ([`SPEC-045`](../../../spec/spezifikation.md#spec-045--statusdateien-der-startscripte-und-ihre-ausweisung), `DevcontainerInspector`, ohne neuen Mechanismus): [`LH-FA-DEV-007`](../../../spec/lastenheft.md#lh-fa-dev-007--container-runtime-im-sandbox-devcontainer) verlangt die Ausweisung jedes Fallbacks in der Befehlsausgabe, und dieser Befehl führt das Startscript aus. „Nicht ermittelbar“ ist kein Fallback.
   - **`down`:** stoppt den Container, den `FindContainer` über das Label liefert (`docker stop`, kein Hilfs-Container, kein Socket-Mount, **keine Lockerung**). Er entfernt weder Container noch Volumes ([`ADR-0015`](0015-sandbox-volumes-pro-instanz.md): der Workspace liegt im Sandbox-Profil in einem Volume). Ist kein Container da oder er schon gestoppt, endet `down` mit Exit 0 (Ausgang wie `u-boot down`: nichts zu tun ist kein Fehler). **Benennung:** `down` bedeutet hier „stoppen“, bei `u-boot down` (Compose) „abbauen“; die Hilfe sagt es. **Gegenoption:** `stop` — passt zum Verhalten, bricht aber die Befehlswahl des Projektinhabers (Freigabe-Punkt b).
   - **Exit-Codes ([`LH-FA-CLI-006`](../../../spec/lastenheft.md#lh-fa-cli-006--exit-codes)):** `2` Aufruf (bare `u-boot devcontainer`, auch mit `--json`; `--dry-run`/`--diff`, weil kein Befehl Dateien schreibt — wie `egress list`); `10` kein `.devcontainer/devcontainer.json` im Basisverzeichnis, ein Basisverzeichnis, dessen Pfad ein Zeichen enthält, das ein `--mount`-Wert nicht trägt (Komma, Anführungszeichen, Zeilenwechsel); `11` Docker-Binary fehlt, Daemon antwortet nicht, Engine nicht lokal; `12` **jeder** Fehler danach (Bau des Hilfs-Images, Start des Hilfs-Containers, `outcome` der CLI ungleich `success`, Fehler eines Lebenszyklus-Befehls einschließlich des Abbruchs von `egress-init.sh` mit dessen Exit 11, `docker stop`); `14` Lesefehler des Dateisystems wie bei den übrigen Befehlen. **Die 12 gilt ohne Auswertung von stderr** (der Engine-Adapter trennt 11 und 12 aus demselben Grund über Vorab-Prüfungen); ein Ladefehler der Feature-Quellen, der semantisch zur 13 gehörte, ist damit nicht gesondert abgebildet (Grenze, nicht gemessen).

4. **Hilfs-Container, Socket-Haltung und Ausweisung.**
   - **Aufruf (Entwurf, S6 prüft):** `docker run --rm --name <u-boot-eigener Name mit Zufallsanteil> --mount type=bind,source=/var/run/docker.sock,target=/var/run/docker.sock --mount type=bind,source=<Ordner>,target=<Ordner> [-e <NAME> …] <Image> devcontainer up --workspace-folder <Ordner> [--remove-existing-container]`. Kein `--privileged`, keine Capabilities, kein `--network`, kein Mount des Home-Verzeichnisses. Es läuft als `root` im Hilfs-Container wie im Messweg (kein `USER`); der Socket ist ohnehin Root-Äquivalent auf der Engine, weitere Härtungen des Hilfs-Containers (schreibgeschütztes Wurzeldateisystem, `no-new-privileges`) sind ungemessen und bewusst nicht Teil.
   - **`--mount` statt `-v`:** `--mount type=bind` bricht bei fehlendem Quellpfad ab, `-v` legte ihn an. Ein Projektordner, den der Daemon nicht sieht (Colima mit Projekt außerhalb des geteilten Bereichs, Docker im Container), ergibt damit einen Fehler (Exit 12) statt eines leeren Bind-Mounts.
   - **Der Projektordner ist schreibgeschützt eingehängt (`readonly`), wenn der Test es trägt.** Ob die CLI nichts in den Ordner schreibt, ist ungemessen; der Umsetzungs-Slice prüft es (S6) und hängt andernfalls schreibend ein, ohne es als Lockerung auszuweisen (Schreibzugriff auf den eigenen Projektordner ist nicht mehr als der Editor-Start) — beides ist im Rahmen dieser Entscheidung.
   - **Umgebung:** Der Adapter reicht nur Variablen durch, deren Name im Text von `.devcontainer/devcontainer.json` als `${localEnv:<NAME>}` vorkommt und die auf dem Host gesetzt sind, als `-e <NAME>` **ohne Wert** (der Wert steht nie in der Kommandozeile des Prozesses; [`LH-FA-DEV-009`](../../../spec/lastenheft.md#lh-fa-dev-009--git-zugangsdaten-im-sandbox-devcontainer): Zugangsdaten nur als Umgebung des Befehls, nie in Image, Volume oder erzeugter Datei). Die Namen extrahiert die Application aus dem gelesenen Text (reine Funktion, ohne Docker testbar), der Adapter bekommt die Liste. Andere Quellen für `${localEnv:…}` (Features, weitere Konfigurationsdateien) sind nicht gelesen und nicht zugesagt. Proxy-Variablen und Registry-Zugangsdaten (private Basis-Images) reicht der Befehl nicht durch (nicht zugesagt).
   - **Lebensdauer:** Der Socket bleibt auf die Lebensdauer des Hilfs-Containers begrenzt. Bricht der Aufrufer ab (Kontext), schickt der Adapter SIGINT an `docker run` (der Client leitet es weiter) und entfernt den Container nach einer Frist mit `docker rm -f <Name>`; ein hängengebliebener Hilfs-Container hielte den Socket offen. Ob ein gestarteter Dev-Container den Socket **nicht** trägt, ist eine Zusage nur mit Docker-Test (Entscheidung 9, Wächter).
   - **Ausweisung ([`LH-FA-DEV-006`](../../../spec/lastenheft.md#lh-fa-dev-006--sandbox-profil)):** Der Hilfs-Container ist nicht das erzeugte Ergebnis; die Anforderung („keinen Container-Runtime-Socket des Hosts einbinden“) bezieht sich auf das, was `u-boot` erzeugt, und bleibt unverändert. Der Befehl weist die Lockerung aus: eine Warnung als Sicherheitslockerung (Kennzeichen `SecurityRelaxation`, wie die Lockerungen von `generate devcontainer`), Text sinngemäß „the host container-engine socket is mounted into a short-lived helper container for this command (root-equivalent access to the engine); the devcontainer it starts does not receive it“. Sie erscheint **vor** dem Start des Hilfs-Containers (ein Abbruch löscht sie nicht), in jedem Ausgang, in dem der Hilfs-Container gestartet wurde, **auch unter `--quiet`**, und im JSON-Umschlag als `diagnostics[]`-Eintrag (`level: warn`, `code` die Kennung der neuen Anforderung; `status: warn`, Exit-Code `0` im Erfolgsfall, wie bei jeder Warnung). `down` startet keinen Hilfs-Container und weist nichts aus. **Gegenoption e (Socket-Proxy mit eingeschränkter API):** Die CLI baut Images, legt Container an und startet sie ([`rohdaten-05-m4.txt`](../../messungen/slice-v1-sandbox-egress-neuladen-entwurf/rohdaten-05-m4.txt)); ein Filter, der das zulässt, begrenzt kaum mehr als der Socket selbst (Argument, nicht gemessen), und er brächte eine zweite Lieferkette. Nicht gewählt.

5. **Pfad-Abbildung: Spiegelpfad.** Der Projektordner wird im Hilfs-Container unter **demselben absoluten Pfad** eingehängt wie auf dem Host und mit diesem Pfad als `--workspace-folder` übergeben. Der Pfad wird unverändert aus dem Basisverzeichnis des Befehls übernommen (keine Auflösung von Symlinks), derselbe Wert geht an den Mount, an die CLI und an `FindContainer`. Damit ist das Label `devcontainer.local_folder` der Pfad des Hosts (das ist der Zweck; **nicht gemessen, S2**), der Bind-Mount des Standardprofils zeigt auf einen Pfad, den der Daemon kennt, und [`SPEC-045`](../../../spec/spezifikation.md#spec-045--statusdateien-der-startscripte-und-ihre-ausweisung) braucht keine zweite Abbildung. Der Quellpfad des Sockets ist der Pfad **auf dem Rechner des Daemons** (`/var/run/docker.sock`; unter Colima gemessen funktionsfähig), andere Socket-Pfade (rootless Docker, `DOCKER_HOST` mit eigenem Pfad) sind nicht zugesagt. Eine entfernte Engine weist der Adapter mit derselben Prüfung wie der Inspector ab (`requireLocalEngine`, Exit 11): ein Pfad des Hosts bedeutet dort etwas anderes. **Gegenoption:** fester Pfad `/w/…` wie im Messweg, den Label und Mount über `--id-label` und `--mount` biegen — die Identität des Containers (`${devcontainerId}`, Volume-Namen, [`ADR-0015`](0015-sandbox-volumes-pro-instanz.md)) hinge dann an Überschreibungen, die kein Editor setzt (S9).

6. **Ausgabe.** Fortschritt (Bau des Hilfs-Images, Ausgabe der CLI) geht auf stderr, unter `--quiet` wird er zurückgehalten und nur bei einem Fehler ausgegeben; die Erfolgsmeldung entfällt unter `--quiet`, die Ausweisung nach Entscheidung 4 und die Fallback-Ausweisung nach Entscheidung 3 bleiben ([`LH-FA-CLI-005`](../../../spec/lastenheft.md#lh-fa-cli-005--verbosity-und-logging) Ausnahmen 1 und 2). Mit `--json` steht genau ein Umschlag auf stdout (`command: devcontainer`, `subcommand: up|down`, `data` mit `containerId`, `remoteUser`, `remoteWorkspaceFolder` bei `up`, mit `containerId` und `stopped` bei `down`); die Fortschrittsausgabe entfällt, bei einem Fehler enthält `diagnostics[].message` das gekürzte Ende der CLI-Ausgabe. `--quiet` ist im JSON-Modus ein No-op (`cli-json-contract.md` §2.2). Der Wert `devcontainer` im Enum von `command` ([`LH-FA-CLI-007`](../../../spec/lastenheft.md#lh-fa-cli-007--dry-run)) ist eine Lastenheft-Änderung im CR. Keine Bestätigungsfrage: `--recreate` entfernt den Container, nicht die Volumes (S4 pinnt das mit einem Marker im Volume); der Neuaufbau im Editor fragt ebenfalls nicht.

7. **Port im Hexagon.** Ein neuer Driven-Port `DevcontainerLauncher` in `internal/hexagon/port/driven/` (`Up`, `Stop`), getrennt von `DockerEngine` (Compose) und `DevcontainerInspector` (lesend): andere Fehlerklassen, andere Vorab-Prüfung. Die Implementierung sitzt im Paket `internal/adapter/driven/docker/` (einzige Stelle mit `os/exec docker …`, `go:embed` des Kontexts); die Application bekommt den Port per Konstruktor und liest die Projektdatei über den Dateisystem-Port; die Importregeln und `depguard` bleiben unverändert (`spec/architecture.md` §4 und §5), `make verify-depguard` ist nur zu laufen, wenn der Umsetzungs-Slice eine Regel anfasst. **Vorab-Prüfung:** Docker-Binary auf dem `PATH`, Daemon antwortet, Engine lokal — **zwei plus eine, nicht drei Schritte**: das Compose-Plugin ist nicht nötig, `Engine.preflight` ist deshalb nicht wiederverwendbar; die Prüfung ist Sache des neuen Adapters. Fehlerklassen: `ErrDockerUnavailable` (11) und `ErrContainerEngineNotLocal` (11) werden wiederverwendet; ein neuer Sentinel `ErrDevcontainerRuntime` (12) steht im Port neben ihnen und wird, wie jeder neue Sentinel, **im Mapper und in `ExitCode` eingetragen** (zwei Klassifikatoren; Pin mit Test). `ErrComposeRuntime` bleibt Compose vorbehalten.

8. **Runtime-Image und Umfeld.** Der Befehl läuft im ausgelieferten Image nicht: `distroless` trägt keine Docker-CLI ([`LH-NFA-PORT-004`](../../../spec/lastenheft.md#lh-nfa-port-004--ausgeliefertes-container-image)); er endet dort wie `up`, `down` und `logs` über die Vorab-Prüfung mit Exit 11 („docker binary not on PATH“). Das Image bekommt weder Docker noch Node (**Option b verworfen**). In einem anderen Container (Docker-Socket des Hosts, anderer Pfad) ist der Spiegelpfad nicht belegt; `--mount` macht daraus einen Fehler, keinen stillen falschen Mount; zugesagt ist es nicht.

## Konsequenzen

- Positiv: Ein Nutzer mit Docker startet und stoppt den Devcontainer mit `u-boot`, ohne Editor, Node oder CLI auf dem Host; der Start nutzt die Referenz-CLI und damit deren Lebenszyklus; Pins und Lockdatei sind Teil des Binary und des Golden Case; ein Abbruch räumt den Socket-Träger ab; jede Zusage hat einen Wächter.
- Negativ: Der Socket ist Root-Äquivalent auf der Engine; der Befehl weist es aus, schließt es nicht. Neue Lieferkette und Pin-Pflege (dritter gepinnter Download im Repo). Der Erststart braucht Netz und Bauzeit (nicht gemessen). Alte Hilfs-Images bleiben liegen. Die Zusage reicht auf Linux so weit wie ein CI-Test und auf Colima so weit wie eine Einzelmessung. `down` heißt anders als `u-boot down`.
- Folgepflicht (eigene Schritte, nicht dieser ADR): Lastenheft-CR (neue Anforderung, Befehlsübersicht, `--quiet`-Ausnahme, Enum von `command`), Fundament (Port, Adapter, eingebetteter Kontext mit Pins, Docker-Tests S2, S5, S6), Befehl (Application, CLI, Handbuch, `CHANGELOG.md`, Docker-Tests S1, S3, S4, S8, S9, Einzelmessung Colima), Spezifikations-Slice nach dem Code (Stellen aus Entscheidung 10). Die Register-Beobachtung zur Pin-Alterung bekommt mit dem Fundament-Slice einen Beleg.
- **Nicht verifiziert (Stand 2026-10-20):** alles unter „Nicht gemessen, nicht zugesagt“ im Kontext. **Akzeptierte Negative, mit Grund:** (1) kein Dauer-Scan des Hilfs-Images (lokal gebaut, nicht ausgeliefert; Ereignis-Trigger); (2) keine Abbildung der Exit-Klasse 13 (ohne Auswertung von stderr nicht trennbar); (3) kein Schutz gegen zwei gleichzeitige Aufrufe für denselben Ordner (nicht gemessen, kein Nutzerbericht); (4) kein Aufräumen alter Hilfs-Images.
